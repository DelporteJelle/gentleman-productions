# Verification Before Completion

## Overview

Before you say "done," "passing," "fixed," or "ready" — run the commands and paste the output. Every time. No exceptions.

**Announce at start:** "I'm using the verification-before-completion skill to confirm this work actually passes."

**Core principle:** evidence before assertions. "Should work" is not a status.

## The Iron Law

```
NO COMPLETION CLAIM WITHOUT VERIFIED EVIDENCE
```

"I believe the tests pass" is not evidence. "I refactored and the logic should still hold" is not evidence. Output from the actual command is evidence.

## When to Use

- About to write "done," "fixed," "passing," "working," "ready to merge."
- About to commit.
- About to open a PR or mark a plan task checked.
- After a change you expect to be safe ("just renamed a variable").

Especially use this when:

- You're tempted to skip because "it's a small change."
- You already ran tests earlier and assume they're still green.
- You're on the last item of a long plan and want to wrap up.

## The Gate

For any claim of completion, run the relevant gate(s) and report the actual last-line output. If you can't paste it, you haven't verified it.

### Python changes (backend-pulse, shared, algo/*)

```bash
python -m pytest --tb=short
```

Run from repo root with the venv active (`source .venv/bin/activate` or use `uv run`). Report:

- Final summary line (e.g. `=== 312 passed, 1 skipped in 18.42s ===`).
- Any failures verbatim — do not summarise as "one failure, unrelated." See [`.claude/rules/no-failing-tests.md`](../../rules/no-failing-tests.md).

Narrowed tests (`pytest path/to/test.py -v`) are fine for debugging, but the final completion claim requires the repo-wide run unless the change is truly localised and you can justify why.

### Frontend changes

```bash
cd frontend && yarn test
```

This runs prettier → eslint → typecheck → jest. All four are part of "passing." A red prettier is a red gate — run `yarn prettier:write`. Report the outcome of each stage (quick to see in Yarn's output).

For type-only verification during iteration: `cd frontend && yarn typecheck` is cheaper, but you still owe a `yarn test` before claiming done.

### Backend-pulse endpoint changed → Frontend

You're not done after the backend tests pass. Run the typegen gate:

```bash
cd backend-pulse && python -m fastapi dev --port 8001    # in another shell
cd frontend && yarn typegen
grep <new_method_name> frontend/src/api/client/sdk.gen.ts # confirm the new shape landed
yarn typecheck                                            # surest signal the regen took
```

Note: `frontend/src/api/client/` is gitignored (regenerated by `yarn build` in CI), so `git diff` and `git status` will not show the regeneration. There is nothing to commit under that path.

Then confirm you did **not** hand-edit any path listed in [`.claude/rules/generated-paths.md`](../../rules/generated-paths.md). If `grep -n "frontend/src/api/client" <your-commit>` shows manual edits, that's a failure — revert and regenerate. See [`.claude/rules/frontend-after-backend.md`](../../rules/frontend-after-backend.md).

### UI changes under `/pick` or `/pack`

Visual verification. See [`.claude/rules/playwright-verification.md`](../../rules/playwright-verification.md):

- Playwright MCP against a running dev server is the default — drive the page, screenshot, inspect.
- Fallback: screenshot of `http://localhost:3000` (or whichever port `yarn dev` binds).
- Konva canvas changes (floor-plan, layout editors): screenshot the canvas region specifically — type checks do not catch shape/z-order regressions.

Do not ask the user to eyeball every iteration. Verify yourself; ask only when the spec leaves a genuine ambiguity (e.g. colour ambiguity between `cargoOrange` and `midnightFreight`).

### C/C++ submodule changes (`algo/heurarchic`, `algo/pyglns`)

Edits to source files inside the submodule do not reach the installed Python package until you reinstall:

```bash
uv sync --reinstall-package ccluster     # for heurarchic
uv sync --reinstall-package pyglns       # for pyglns
```

Then confirm the rebuilt module actually loads:

```bash
python -c "import ccluster; print(ccluster.__file__)"
python -c "import pyglns; print(pyglns.__file__)"
```

Only then run the tests. "It compiled" is not the same as "the binding picked up the change." See [`.claude/rules/python-uv.md`](../../rules/python-uv.md).

### MongoDB query changes

If you added a filter, sort, or lookup on a new field, confirm the nearest `.indexes.mongodb.json` was updated — see [`.claude/rules/mongodb-indexes.md`](../../rules/mongodb-indexes.md). An unindexed query passes unit tests (mongomock doesn't enforce indexes) and breaks production. Verify by grepping for your new field name across `.indexes.mongodb.json` files:

```bash
grep -rn '"your_field_name"' $(find . -name '.indexes.mongodb.json')
```

### Harness drift (Pulse-specific completion step)

Before claiming done, ask: **did my change touch anything the harness tracks?**

- A new service, router, feature directory, subsystem CLAUDE.md, rule under `.claude/rules/`, deprecated path, or generated path?
- A new skill under `.claude/skills/`?
- A new hook under `.claude/hooks/`?

If yes, invoke the [`maintaining-pulse-harness`](../../skills/maintaining-pulse-harness/SKILL.md) skill to confirm the relevant harness surface is consistent with the code change. Not doing this leaves the harness lying about the codebase, which breaks downstream skills and subagents that trust it.

## Red Flags

If you catch any of these thoughts, stop and run the gate:

- "The tests might be flaky." → Run them three times. If they're actually flaky, that's a separate bug to file.
- "That failure is pre-existing." → Prove it. Checkout `origin/<base-branch>` (per [`.claude/rules/base-branch.md`](../../rules/base-branch.md)), run the failing test, capture the result.
- "I'll verify after committing." → No. Verify before. The commit message "fix X" is a claim; back it with evidence.
- "The change is too small to need tests." → TDD discipline exists precisely because "small and safe" has a 10% bug rate.
- "It worked in the last run." → Changes since then? Environment churn? Another process? Rerun.
- "Yarn test is slow, I'll just run jest." → `yarn test` catches formatter and lint regressions jest won't. Pay the full cost.

## Common Rationalisations

| Excuse | Reality |
|--------|---------|
| "Just a rename, no behaviour change" | Renames break imports, test discovery, serialisation. Run the suite. |
| "Only changed a comment" | Fine — but still at least `yarn prettier:check` / `git diff` for whitespace regressions. |
| "I ran it five minutes ago" | Five minutes of new edits can break it. Rerun. |
| "CI will catch it" | CI is slow, and PR author cost is high. Catch it now. |
| "The test I added is the only one that matters" | Regressions happen in tests you didn't think to run. |

## Checklist Before Claiming Done

```
[ ] Relevant gate ran (python -m pytest --tb=short, cd frontend && yarn test)
[ ] Final output captured — not paraphrased, not inferred
[ ] No failures, or failures proven pre-existing with evidence
[ ] Backend-pulse change → yarn typegen ran → no unstaged client diff
[ ] No hand edits to generated paths
[ ] UI change → screenshot / Playwright verification done
[ ] C/C++ change → uv sync --reinstall-package <name> → import confirmed
[ ] Mongo filter/sort on new field → .indexes.mongodb.json updated
[ ] Harness surface touched → maintaining-pulse-harness invoked
[ ] Self-review on git diff — no stray debug prints, no commented-out blocks
```

A single unchecked box means not done.

Paste the output. If you can't paste it, you didn't verify it. If you didn't verify it, you aren't done.
